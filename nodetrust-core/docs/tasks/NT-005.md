## Behavior

`resolve_declaration(name, spec, versions)` returns `spec_type`, target name,
all matching observed `candidate_versions`, resolution, and an unresolved reason.
`resolve_registry(connection, exact_root)` follows these candidates transitively
with a visited set. Roots absent from the snapshot are rejected. Output has
exact identity nodes, NT-003-compatible resolved edges, unresolved declaration
records, and explicit truncation reasons. Strip `reason` from unresolved records
when validating against the closed NT-003 dependency-edge reference schema.

```python
from nodetrust.contracts import PackageId
from nodetrust.resolver import resolve_registry
from nodetrust.storage import Database

db = Database("data/nodetrust.db")
with db.transaction() as connection:
    graph = resolve_registry(connection, PackageId("npm", "your-package", "1.0.0"))
print(graph.to_dict())
```

The database must already contain the package metadata. The resolver does not
fetch from npm or synthesize versions. Use a transaction for a consistent
snapshot during concurrent ingestion. Default limits: 1,000 nodes, 10,000
resolved/unresolved edge records, 25 hops. A limit means partial/unknown coverage.

- All matching versions are possibilities; highest version is not assumed installed.
- Existing `dependencies_of` retains `possible_version` for compatibility, and
  adds candidate versions, spec type, and unresolved reason. Its single highest
  candidate remains a display convenience, not client evidence.
- Aliases resolve to their real scoped/unscoped target while preserving the declaration.
- Tags, alias tags/omitted alias specs, git/file/workspace references, invalid
  ranges, and absent matching versions remain unresolved. No tag lookup is guessed.
- Optional declarations override duplicate production declarations as in the
  existing normalizer. Peer and optional candidates are conditional: this is
  not an npm peer constraint solver, platform selector, or install layout.
- Cycles and diamonds preserve edges but visit each package version once.
- Full version text (including build metadata and leading v) is preserved per
  NT-003; semver precedence ignores build metadata. Equal-precedence candidates
  use deterministic lexical ordering. This is not an identity migration.
- Client lockfile/SBOM parsing remains the source of observed client versions;
  a registry candidate cannot rewrite a client scan. Reachability does not prove exploitability.

The legacy centrality projection still picks the highest version and belongs to
NT-013. This task supplies the reusable complete-candidate resolver and uses it
in NT-004; it does not replace every existing stand-in graph algorithm.

## Range fixes and verification

Invalid numeric prerelease identifiers, numeric components after wildcards,
malformed aliases, and dist-tags embedded in unions no longer create guessed
matches. Normalization retains the entire declared spec: cutting it at 200
characters could previously remove a restrictive comparator.

`fixtures/nt005/semver-reference.json` contains **1,161** comparisons generated
from local **node-semver 7.8.5**, default strict/prerelease settings. Python tests
compare every result with that independent oracle. This is a finite compatibility
matrix, not a claim of complete npm parser equivalence.

Reference: [npm/node-semver](https://github.com/npm/node-semver).
To deliberately regenerate the fixture with an installed oracle:

```bash
node scripts/generate_semver_reference.cjs /path/to/node_modules/semver
python -m pytest tests/test_resolver.py tests/test_semver.py
python scripts/check.py
```

Additional tests cover schema compatibility, missing dependencies, cycles,
transitive closure, scoped aliases, peer/optional declarations, exact client
evidence, node/edge/depth limits, and preservation of long specs.

The existing SMTP test certificate fixture gained Subject/Authority Key
Identifiers to pass Python 3.14 strict X.509 validation. TLS verification remains
enabled and untrusted certificates still fail before credentials are sent.
